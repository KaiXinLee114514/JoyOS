# JoyOS 的文本编码现状

这份文档回答一个问题:**JoyOS 里的文字到底用的是什么编码,合不合标准?**

一句话答案:**字符编号是标准 Unicode 码位,内核文本也已经是标准 UTF-8** ——
字符串可以原样 `db` 进内核,和磁盘上的文件、编辑器、git 一致,别人不用再学一套。

> 历史:中间有一段时间内核存中文用的是"每个码位一个 u32"的数组(查表快但和外界不一致),
> 第 2.2、2.3 节保留了对那套表示和它的坑的记录,第 6 节是改成 UTF-8 的做法与实测结果。

下面把每个环节拆开讲清楚,并且标出哪些是标准、哪些是我们自己定的。

## 1. 速览

| 环节 | 用的什么 | 标准吗 |
|---|---|---|
| 字库源数据 `font/unifont-subset.hex` | GNU Unifont 的 `.hex` 格式(`码位:点阵`) | ✅ 标准(别人能直接拿去用) |
| 字库二进制 `font/font-joyf.bin` | 自定义容器 JOYF;**键 = Unicode 码位** | ⚠️ 容器自定义,键标准 |
| 内核里的英文/ASCII 字符串 | 普通的 0 结尾字节串 | ✅ 合法 UTF-8(ASCII 是它的子集) |
| 内核里的中文文案 | **UTF-8 字节串**(`db '你好，世界！', 0`) | ✅ 标准 |
| 终端打印接口 | `term_print` 先 UTF-8 解码成码位,再统一 `term_print_cp` | ✅ 中英一条路 |
| 文本模式那套"字模号 0x80 起拼两格" | VGA 字模槽索引 | ❌ **这不是编码**,是硬件槽位 hack |
| 键盘输入 | PS/2 扫描码 → 直接映射成 ASCII | ⚠️ 只能输入 ASCII(没有输入法,见 2.4) |

## 2. 逐个说清

### 2.1 字库:键是标准码位

`tools/unifont2bin.py` 把 Unifont 的 `.hex` 转成内核能直接 `incbin` 的 JOYF 格式:

```
+0  'J''O''Y''F'   +4 版本   +8 字形数   +12 数据区偏移
每项 12 字节:码位(u32) 宽(1) 高(1) 保留(2) 数据偏移(4),按码位升序
数据:8 宽每行 1 字节,16 宽每行 2 字节,最高位在最左
```

查一下就知道键就是 Unicode 码位:

```
查 'A'  → U+0041 宽 8  高 16
查 '你' → U+4F60 宽 16 高 16
查 '好' → U+597D 宽 16 高 16
```

**容器格式(JOYF)是我们自己定的**,不是标准位图字体格式(BDF / PCF / PSF / Unifont `.hex` 才是)。
这么做只是为了内核里查表简单:定长表项 + 按码位升序 → 二分查找,不用解析文本格式。
源数据仍然是标准的 `.hex`,所以数据本身没有被我"私有化"。

### 2.2 内核里的中文:码位数组,不是 UTF-8

> ⚠️ **这一节记录的是改造前的状态**(留作历史与踩坑记录);改造已经在第 6 节完成。

中文文案由 `tools/unifont2bin.py` 生成成**码位数组**(`font/vga-zh-strings.asm`):

```asm
zh_str_1:
    dd 0x00004F60, 0x0000597D, 0x0000FF0C, 0x00004E16, 0x0000754C, 0x0000FF01, 0
    ;  你          好          ，          世          界          ！        结尾
```

这个表示:

* 每个字符固定 4 字节、小端存放码位 → 相当于**内存里的 UTF-32LE**
* 没有 BOM,用 0 双字结尾(不是长度前缀)
* 因此它**不是**任何标准的"文本字节流"格式:UTF-32 作为文件/交换格式通常带 BOM,
  而我们是内存数组 + 0 结尾,更像是"内部表示"而不是"编码"

打印走的是 `term_print_zh`(esi = 数组首地址)→ 逐项调 `term_print_cp`(eax = 码位)
→ 图形模式进 `fb_putcp` 查字库 blit,文本模式查字模号表。

### 2.3 终端不吃 UTF-8(有实证)

> ⚠️ **这一节记录的是改造前的状态**(留作历史与踩坑记录);改造已经在第 6 节完成。

`term_print` 是 `lodsb` 逐**字节**取,然后 `term_putc`:

* 文本模式:字节直接当字符码写进 `0xB8000` → 于是 UTF-8 中文显示成带音符的拉丁字母
  (这是早期那版截图上"乱码"的来源)
* 图形模式:字节当码位查字库 → 查不到就画**缺字方框 □**(`fbterm.asm` 里的 `missing_glyph`)

所以给 `term_print` 塞 UTF-8 中文,现在的结果是**一排方框** —— 这个现象在开发过程中出现过,
可以当作"没走 UTF-8 路"的标志。

### 2.4 键盘:只有 ASCII 路径

`kernel/keyboard.asm` 把扫描码查表映射成字符,表里就 ASCII(0x20-0x7E)+ 回车/退格/制表。
没有输入法、没有组合键、更没有"输入一个 Unicode 码位"的通道 —— 所以在 shell 里**打不出中文**,
只能显示代码里写死的中文。

### 2.5 那个"字模号拼两格"不是编码

文本模式那条实验路里,汉字被劈成左右两半、放进 VGA 字模表的 0x80 起两个槽,打印时连写两个
字节。**那两个字节是硬件字模槽号,不是字符编号** —— 同一个汉字换一套字模表,槽号就变了。
只有在文本模式实验(`make run-font`)里才用,正式路径(图形模式)是按码位查表的。

## 3. 为什么当初这么选

* 一开始只是要显示**固定的几句中文文案**,码位数组查表最快,不用写解码器
* 查表接口天然是"码位"的,所以字库那边一开始就是标准的
* 代价是**和外界交换文本**这条路被堵住了(磁盘上的 UTF-8 文件、git、编辑器都不认我们这套)

这是取舍,不是疏忽:当时的目标是"屏幕上出现中文",而不是"做一个能读文件的系统"。

## 4. 想标准化该怎么做(**已按这一节做完**,见第 6 节)

改成一个 **UTF-8 解码器**,把"字节流 → 码位"这一步补上。**字库和码位表一个字都不用改。**

1. **`kernel/utf8.asm`**(新,约 30-40 行)
   * `utf8_decode`:进 esi 指向字节流,出 eax = 码位,esi 前进 1-4 字节
   * 1 字节 `0xxxxxxx`、2 字节 `110xxxxx 10xxxxxx`、3 字节、4 字节
   * 非法序列(截断、非法前导、超范围、过长编码、代理区)→ 返回 U+FFFD(`�`)
2. **`term_print` 改造**:循环 `utf8_decode` → `term_print_cp`,中英统一一条路
   * 文本模式照旧走字模号表(它本来就按码位查)
   * 于是两种显示模式都自动支持 UTF-8
3. **文案生成改一下**:`tools/unifont2bin.py` 增加"输出 UTF-8 字节串"的模式,
   `font/strings.txt` 原样 `db` 进内核(`db '你好，世界！', 0`),不再是 `dd` 码位数组
4. **回归验证**:现在那 6 行中文的**逐像素模板匹配**正好当回归测试 ——
   换了编码,屏幕上应该**一模一样**,一条断言都不用改
5. 顺手能加的用例:
   * 4 字节序列(比如 U+1F600 😀):需要把对应字形也加进字库子集(Unifont 有)
   * 故意截断的字节序列 → 期望画成 `�`

做完之后:"字库按码位索引" + "内核文本 UTF-8" 就都标准了,
以后接 FAT12 读 UTF-8 文件、写个 `cat`/`echo` 都顺理成章。

## 5. 一句话备忘(现状)

* **码位**:一直是标准 Unicode ✅
* **字库源** `.hex`:标准 ✅;容器 JOYF:自定义但键标准 ⚠️
* **内核中文文本**:**标准 UTF-8** ✅(`db '你好，世界！', 0`,见第 6 节;
  改造前的"码位数组"留在 2.2 当历史)
* **磁盘上的文本文件**:标准 UTF-8 ✅(`cat` 直接打,`write` 原样存)
* **字模槽号**(文本模式那条实验路):不是编码 ❌

## 6. 已经做了:内核文本统一 UTF-8

上面第 4 节的方案已经落地(`kernel/utf8.asm` + `term_print` 改造 + 文案生成改 `db`),
现在的状态:

```asm
zh_str_1:
    db '你好，世界！', 0        ; ← 就是标准 UTF-8 字节串,原样从 font/strings.txt 来
```

* **`kernel/utf8.asm`**:`utf8_decode`(esi = 字节流 → eax = 码位,esi 自动前进)
  * 1/2/3/4 字节序列都解,ASCII 只是它的一个特例
  * 三个合法性检查:非法前导 / 截断序列 / 过长编码 / 代理区(D800-DFFF)
  * 坏字节返回 **U+FFFD(替换字符 `�`)并只前进一个字节** —— 数据中间烂一段,后面的文字照样显示,
    不会卡死(实测:截断的 3 字节 + 一个孤立延续字节 → 屏幕上两个 `�`,后面的英文继续显示)
* **`term_print`**:循环 `utf8_decode` → `term_print_cp`,于是
  * 图形模式:`fb_putcp` 按码位查字库 → blit
  * 文本模式:按码位查字模号表 → 写 `0xB8000`
  * 两种模式**自动都支持 UTF-8**,中英一条路,控制字符(`\n \r \b`)在 `term_print_cp` 里分流
* **4 字节也验证了**:😀(U+1F600)在字库里是 16×16,实测能画出来
* **回归测试**:原来那 6 行中文的**逐像素模板匹配一条都没改**就继续通过 —— 换了编码,
  屏幕上的像素应当一模一样,这正是最好的回归证据;另外新增了三个断言:
  UTF-8 三字节(汉字)、四字节(emoji)、坏字节(替换字符)

还没做的(不影响"编码标准"这件事):

* 键盘仍然只出 ASCII(要中文输入得做输入法,那是另一个工程)
* 键盘没有输入法(同上)
* 磁盘上的文本文件现在可以读了:shell 的 `cat <文件>` 就是把 FAT16 读出来的
  UTF-8 缓冲区直接丢给 `term_print`(见 [filesystem.md](filesystem.md))——
  `progs/README.TXT` 里那些中文就是这么显示出来的
